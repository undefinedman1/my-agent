## 二、第一步：判定冲突是“重构引入”还是“原本就有”

这一步不能跳过，两种情况处理方式完全不同。

- **重构引入**：拆分模块 / 改依赖方向时，两条路径各自引入了同一库的不同版本 → 对齐版本即可，风险低。
- **原本就有（隐性 blocker）**：一直没暴露，重构把它推到台前 → 说明模块边界本身有问题，光对齐版本可能掩盖更深的问题（见第 4 节）。

判定方法：拿重构起点的 commit 和当前分支，各跑一次依赖树，只 diff 版本变化项。

```bash
# 当前分支
mvn -q dependency:tree -Dverbose -DoutputFile=tree-now.txt

# 重构起点（用 worktree，避免污染工作区）
git worktree add /tmp/base <refactor-base-commit>
cd /tmp/base && mvn -q dependency:tree -Dverbose -DoutputFile=/tmp/tree-base.txt

diff /tmp/tree-base.txt tree-now.txt
```

只看两点：**冲突的那个 artifactId 是否出现在 diff 里**、**它的版本是从哪个模块被拉进来的**。

单查某一个包：

```bash
mvn dependency:tree -Dverbose -Dincludes=<groupId>:<artifactId>
```

（`-Dverbose` 在 Maven 3.x 上会显示被 omitted 的冲突版本和冲突原因，这是关键信息，不要省。）

## 三、第二步：按优先级选解决手段

从“最不容易产生副作用”到“最容易埋坑”，依次尝试：

1. **统一收敛到 `dependencyManagement`（多模块最佳）**
   在父 POM 或专用 BOM 模块里 pin 死版本，所有子模块继承。这样版本只有一个事实来源，后续不会各模块漂移。
2. **导入官方 BOM**
   如果冲突的是 Spring / Jackson / Netty 这类有成套 BOM 的栈，直接 `<scope>import</scope>` 导入官方 BOM，比逐个 pin 安全得多（避免只对齐一个包、破坏同栈内的版本配套关系）。
3. **`<exclusions>` 精确切断传递路径**
   适用于“某个依赖带进来的老版本根本不需要”。比全局 force 更局部，副作用最小。要注意：排除后必须验证运行时行为，不只是编译通过。
4. **`maven-enforcer-plugin` 把规则固化到 CI**
   ```xml
   <rules>
     <dependencyConvergence/>
     <requireUpperBoundDeps/>
     <banDuplicateClasses/>
   </rules>
   ```
   这一步的价值不是“解决本次冲突”，而是**防止重构后再次漂移**——重构期最容易反复回归的问题就是版本。
5. **最后才考虑 `force` / resolutionStrategy 强压**
   强压会让“编译通过但运行期 `NoSuchMethodError` / `NoClassDefFoundError`”的风险变高，且下一个人很难看出为什么版本不对。

Gradle 生态对应命令（如果是 Gradle 请忽略 Maven 部分）：

```bash
./gradlew dependencyInsight --dependency <name> --configuration runtimeClasspath
# 解决：platform()/enforcedPlatform()、constraints、resolutionStrategy.force
```
